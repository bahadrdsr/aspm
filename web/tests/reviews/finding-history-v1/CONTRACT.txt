Exact native API
----------------
GET /api/v1/findings/{id}
GET /api/v1/findings/{id}?notesCursor=<id>
GET /api/v1/findings/{id}?observationsCursor=<id>
Both cursor keys may appear in the same existing GET. There is no limit,
page/offset, history endpoint, server revision, timestamp or query API.
Nonempty cursors are 32 lowercase hexadecimal characters; empty/omitted
selects the first page. Unknown/duplicate query keys are rejected by this
explicit UI fixture route allowlist.

The real handler reads canonical finding metadata, then separate observation
and note queries. Each is id > its own cursor, ORDER BY id, LIMIT 501.
The public DTO contains up to 500 records per stream plus:
  notesNextCursor: null | last returned note ID
  observationsNextCursor: null | last returned observation ID
The nonnull cursor means a further record exists. There is no total count and
no atomic history/finding snapshot guarantee. JSON returns the full canonical
finding, both stream pages, apiVersion and dataOrigin each time.

Note shape remains {id,text}, with no invented author/timestamp/revision field.
Observation shape remains id/runId/sourceId/scanId/scope/sourceScanAt/
sourceFindingId/sourceSeverity/normalizedSeverity/sourceLocation/impact/
remediation/unmapped/evidenceDigest. Nested literal JSON and original source
variants must survive; unknown source time remains null. Source date,
collection/import time and human workflow/inference are distinct.

POST /api/v1/findings/{id}/notes remains {text} only and returns 201 {note}.
Text is nonblank/NUL-free, at most 8192 UTF-8 bytes; encoded body is 32 KiB.
PATCH /api/v1/findings/{id} retains existing intentional finding fields and
the 16 KiB body limit. This narrative only changes workflowState. Its complete
canonical response has normal first-page note/observation arrays, not all
previously loaded history. Neither mutation supplies a server revision.

Synthetic data and two independent frontiers
-------------------------------------------
503 notes and 507 observations use server-native IDs/order. Initial GET thus
really truncates both streams at 500. Two distinct note IDs have identical
multiline text, including literal markup/URL and multibyte characters.
Observations carry varied scopes/branches/revisions, severities, known/unknown
source times, locations, nested arrays/objects/booleans/null in unmapped JSON.
No customer data or real credentials occur.

Add separately labelled Load more observations and Load more notes controls
inside the current dialog. Each advances its own actual returned cursor.
For the tested manual UX, the inactive query cursor may be omitted/empty or
repeat that stream's previously requested cursor, but must not silently advance
an as-yet-unrequested inactive frontier. Every native response is still merged
by ID, even when it repeats another stream's first page or returned tail.

Loading one cursor never replaces the other stream's loaded records. Its
repeated first-page nextCursor must not rewind the other's exhausted frontier.
Different note IDs with the same text remain separate. Returned pages and
acknowledged notes cannot be duplicated by overlapping canonical responses.
Show actual loaded/supplied counts, not an invented total or full-directory/
atomic-snapshot claim. No automatic cursor draining or polling.

Errors and authority
--------------------
A pending/503 continuation keeps both confirmed loaded histories and original
source facts. Its scoped error/retry preserves the exact failed query.
It is not an empty page, permission denial or successful completion.

403/404 detail denial withholds protected source/history metadata, including
hidden cached lists, through subsequent 503 retries until a new authorized
read succeeds. A title already supplied by the separately authorized Work
row is not treated as fresh denied-detail data. Error recovery may reread the
failed cursor or reset explicitly; it cannot reveal old source records before
successful authorization.

Viewer can read/load history but not add notes or change workflow. Current
server roles are independent from cached session-role metadata. Workspace,
logout and 401 clear the dialog/history/drafts and discard old responses.
Held pages must be aborted on close/scope loss; releasing a late old response
must not expose Alpha source/notes in Beta or after sign-out.
Only the unchanged theme preference may be browser-persisted.

ACK/read ordering, not fabricated revision guarantees
----------------------------------------------------
An old observation continuation is captured before a new note and workflow
mutation. The note's 201 ACK adds its actual returned ID immediately. The
workflow ACK supplies canonical metadata and default capped arrays, including
an echo of that new note. Neither it nor the older page may remove loaded
records, duplicate the note, roll back human workflow or relabel source state.

The new synthetic note ID falls in a valid existing ID gap. A returned first
page may therefore shift its boundary. The prior continuation frontier and
loaded records are not replaced by this bounded PATCH response.
The two pre-existing same-text notes plus the acknowledged third note must
remain three distinct records once both pages have been read.

After those ACKs, another explicitly requested history GET has newer canonical
metadata: a human workflow update and source description/freshness snapshot.
The UI must accept that later authorized snapshot rather than permanently pin
all metadata to a prior local ACK. The tests provide HTTP response data only;
they add no client/API-state replacement or fake server revision. A separately
loaded Work row need not masquerade as a globally atomic copy of later detail.
