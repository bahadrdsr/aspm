Reason and evidence
-------------------
The astra-focused-20260930-01 run passed WP1/WP2/WP4. WP3/WP6 stopped at
finishEntry line 52: the ledger contained two scheduled bare Work 200s with
null failures. The raw traces actually include an aborted first request.
The fixture registered the request only after awaiting allHeaders, so an early
requestfailed event could be missed. A1 registers before that await, seeds only
the real Request.failure value, and records response/requestfinished events.
History BASELINE.json preserves this distinction and source artifact hashes.

DECISIONS.json historically required exactly one nonaborted entry completion
and an actual abort for any extra. That observation is not a transport invariant:
StrictMode cleanup can race a completed read. A1 admits at most two explicitly
declared bare scoped entry calls, requires at least one completed observed 200,
and accepts only completed 200s or actual abort failures for the other call.
The cohort closes after a confirmed 50-row render. No extra requests, delay in
production, deduplication, StrictMode change, automatic drain or cap change.
WP1's final ledger assertion counts the bounded entry cohort plus exactly the
two explicitly requested continuations, rather than assuming one live entry.

WP5's first held detail 401 was consumed by a request with net::ERR_ABORTED.
Its second GET for the same finding took the default 200 response. No live 401
reached the App, so waiting for Sign in did not test production 401 behavior.
A1 declares two held 401 responses in one path/workspace-specific denial cohort.
While active, that path cannot use default 200, including after an earlier 401
changes synthetic authentication. A third request is rejected and ledgered.
Other detail defaults, authentication, Work errors, ACKs and refresh stay intact.
The case requires an actual 401 response event while the request is nonaborted,
real App Sign in, stale Work abort and no protected restoration before closure.
