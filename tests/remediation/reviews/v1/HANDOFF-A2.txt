Read-only runtime evidence, not a source-text assertion
------------------------------------------------------
The tracer observes actual pgx query start/end events on an explicitly marked
test request. It classifies workspace/membership row-lock queries only for the
random owned schema. It records no SQL arguments, credentials, response values
or raw SQL. A workspace lock counts only after actual successful completion,
one returned row and a real active transaction on the same backend PID.
Transaction boundaries reset the observation.

Before any insertion membership-lock query executes, the tracer checks that
completed workspace-row protection has already been observed on that same
transaction/connection. If not, it cancels ONLY the owned insertion request
immediately. The competing membership update is never started on this unsafe
branch. This prevents staging the known inverse lock cycle.

If correct order is observed, the tracer places a bounded scheduling hold
after the workspace row-lock query has actually completed. It changes no
database state or returned result. A second actual API request then makes a
benign admin -> admin membership update using the normal session, Origin and
workspace authorization headers.

The test observes pg_blocking_pids for those two owned backend PIDs through an
independent real PG connection. The workspace writer must be waiting on the
insertion's already-acquired row protection. This is a safe one-way wait, not
a deliberately staged deadlock. Releasing the tracer hold allows membership
locking/insertion/commit first, then the same-role update. Both operations must
complete normally and the real session must still show admin membership.

Bounds and cancellation
-----------------------
Only two operation variants are run. Each uses its own random remediation
schema and existing bounded cleanup. Each observed API request has a three-
second context. Holds end on explicit release or context cancellation. PG
blocker inspection lasts at most 500ms with at most 25 read-only probes.
Cancellation paths release holds and drain owned requests within fixed bounds.
There is no load/DoS loop, shared-schema target or database role/policy change.
The requested admin -> admin API update never changes effective permission.
The new test starts no worker and makes no vendor request. Enqueue setup uses
the existing real local intake fixture only to create a canonical finding.
