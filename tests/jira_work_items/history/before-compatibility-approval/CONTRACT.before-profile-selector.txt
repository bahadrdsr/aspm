EXTENSION AND EXACT API
Extend existing connections, delivery outbox/history and DeliveryWorker, not a
parallel Jira service. Reuse app.Open, sessions/membership, leases/fences,
integration crypto and connectors.OpenDelivery; no new constructor is required.
Existing Slack requests, DTO keys, worker behavior and UI stay unchanged.

POST /api/v1/integrations/connections:
{profile:"jira-cloud-v3",name,enabled,token,jira:{
 credentialType:"oauth2-bearer",cloudId,apiBase,siteOrigin,project,issueType,
 fieldMappings:{"customfield_10010":"asset.name"}}}
All fields are explicit. Current workspace admin alone configures connections.
PATCH /api/v1/integrations/connections/{id} accepts name/enabled/token/jira;
whole jira target replaces atomically, omission preserves, null is invalid.
Real changes increment revision once. Profile/workspace/id/revision/approval
are server-owned. Reject empty/scheme-prefixed credentials, arbitrary metadata,
headers, Slack channel on Jira and Jira target on Slack. No secret readback/logs.
Jira GET/list retain common metadata with channel:"", add jira and
permissionState:"not-verified". Metadata never certifies Jira permission.

POST /api/v1/findings/{id}/delivery-previews with {connectionId} returns 200:
{preview:{workspaceId,findingId,connectionId,connectionRevision,profile,
 requestedBy,jira,payload:{title,body,deepLink,fields},bindingDigest,
 nativeValidation:"not-run",reviewRequirements:[
 "explicit-queue-consent","native-required-fields","jira-permission"]}}
This is LOCAL payload review: no native GET/POST and no persisted intent.
bindingDigest is "sha256:" plus 64 lowercase hex digits of the server binding:
workspace/finding/actor/connection/revision/profile/target/resolved payload.
No separate preview service is needed; queue recomputes and compares the digest.

Jira POST /api/v1/findings/{id}/deliveries requires exactly
{connectionId,idempotencyKey,previewDigest,confirm:true}; 202 means durable queued.
Slack keeps its existing {connectionId,idempotencyKey} request unchanged.
Current admin/analyst can preview/queue their scoped finding; viewer reads but
cannot write. Cross-scope IDs are 404. Missing/false consent and forged routing,
actor, payload, prior or approval are 400. Disabled/changed selection is 409.
Identical replay is 200 with the same intent/receipt, including after reopen;
same workspace key with different finding/actor/revision/target/payload is 409.
No auto-generated replacement key, automatic retry or exactly-once remote claim.

NATIVE PROFILE, APPROVED TARGET AND FIELD CONTRACT
Use the existing jira-cloud-v3 OAuth bearer profile, NOT email/API-token Basic.
cloudId is a lowercase UUID; project is uppercase native KEY; issueType is a
positive decimal native ID. apiBase is an explicit canonical HTTPS origin plus
exactly /ex/jira/{cloudId}, without credentials/query/fragment/encoded routing.
This is the Atlassian OAuth gateway shape; a separately approved gateway may
retain it. siteOrigin is an explicit HTTPS browser origin, never a credential
destination. Admin selection approves only the exact workspace target, not a
global provider permission. Dispatch needs the existing explicitly approved
normal-TLS/direct client. No default client/transport, ambient secret, endpoint
fallback, redirect, proxy, tenant discovery, credential refresh or HTTP downgrade.
Jira credentials must not reach Slack or another origin.

Mappings have <=16 keys matching ^customfield_[0-9]+$ (<=128 bytes).
Sources are only finding.id, finding.title, finding.severity, asset.name and
finding.deepLink, resolved to strings. No literals/templates/scripts, arbitrary
property paths, objects or reserved project/issuetype/summary/description keys.
Payload title is canonical finding title, body is
"Severity: <severity>\nAsset: <name>", and deepLink is trusted PublicOrigin +
"/#/work?finding=" + escaped finding ID. Reject summary >255 runes at preview/
queue, without truncation. Source text is inert ADF text, never instructions.
No raw report, source code, evidence, notes, remediation, secret or AI auto-export.

DURABLE DISPATCH
Only Jira delivery DTOs add jira and createAttemptedAt; their payload adds fields.
Trusted approvalRef, exact target/profile, actor, user key and payload binding
survive reopen. Recompute stored binding and freshly check role, enabled/revision,
target/profile/credential identity at dispatch, before create and before receipt
commit. Corruption/routing mismatch fails before I/O.
Worker calls existing native Preview (GET createmeta) before Send (one POST).
Bound metadata to <=4 pages, <=50 fields/page, <=64 KiB/body. No SQL connection,
transaction or row lock may survive a metadata, POST or response-body wait.
Commit create_attempted_at under the current fenced lease BEFORE external create.

Missing/unsupported required fields: failed/required_fields, sorted
failure.missingFields, failure.stage:"metadata", retryable:false, ZERO POST.
Native POST 400 field errors use stage:"create"; 401/403 are failed/auth;
429 is rate-limited/rate_limited with literal bounded Retry-After. Empty/malformed
receipt, lost ACK, timeout or 5xx after create is uncertain, never fake success.
Failure keeps code/nativeCode/httpStatus/retryAfterSeconds/retryable plus
Jira-only stage/missingFields, not vendor bodies/messages/secrets.
Confirmed receipt remoteId is the native issue key exposed by the adapter
(SYN-42), not a fabricated numeric ID. Derive remoteUrl from approved siteOrigin
+ "/browse/" + key; never trust arbitrary native self as the browser link.

Role loss, disablement or credential/target revision cancels held context-honoring
Jira I/O within one second. Before create: blocked with authorization-revoked,
connection-disabled or connection-changed, no createAttemptedAt. After possible
create: uncertain, no accepted receipt/resend. Natural lease expiry/crash fences
the old owner against late commits/resends. Regrant cannot resurrect terminal
work. Finding workflow/source/verification/evidence/notes remain unchanged.

EXPLICIT OWNED-ROW SQL FAULT EXCEPTION
Ordinary CRUD/intake/preview/consent/native creation still use real APIs/workers.
Fault injection may UPDATE only this fixture's already API-created
integration_connections/finding_deliveries rows. Require the owned random schema,
workspace_id AND id, lock/select exactly one row, and require RowsAffected=1 for
every successful UPDATE. No INSERT/business seeding or other-user/schema/policy/
permission mutation is authorized by this exception.
J4 enumerated committed faults: delivery payload.title, approval_ref,
idempotency_key, binding_digest; connection jira_target.apiBase; and a delivery's
profile/channel/jira_target changed together to a valid-but-unapproved Slack tuple.
J5 validates old Slack/null-Jira and new Jira tuples using scoped no-op UPDATEs
that affect exactly one row and are rolled back. Its invalid profile/channel/
jira_target tuples first lock exactly one row, must fail an approved named CHECK
with SQLSTATE 23514 and zero affected rows, and are rolled back. Verify original
old values afterward. These are real, scoped SQL fault/probe writes, not a
zero-SQL-writes claim. Separate empty owned predicate probes calibrate catalog
deparse/read-only tuple evaluation only; they do not stand in for V9/V10 migration.
