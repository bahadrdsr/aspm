URL, credential and native protocol boundary
-------------------------------------------
The complete original URL, including every query value, is secret.
Use shared AES-256-GCM key/envelope (32-byte independent integration key;
byte(1), nonce, ciphertext/tag), with Teams-specific AAD:
"aspm/teams-workflow-credential/v1\0<workspace>\0<connection>".
Do not alter Slack/Jira AAD/version or derive a key from another credential.
DB privacy observations exclude ONLY credential_ciphertext, not target/payload.
They prove absence outside that envelope, not key-rotation authorization.

URL <=16384 bytes, explicit canonical HTTPS origin, valid port, nonempty callback
path other than "/", no userinfo/fragment/opaque form/controls. Canonical origin
uses lowercase host, no trailing dot or explicit default :443, and a canonical
nondefault decimal port. No provider/cloud hostname guess. The existing adapter
also bounds decoded path to 4096 bytes and rejects dot segments, repeated slashes,
backslash, encoded routing separators, double-encoded routing and decoded
controls. Safe escaped path letters remain valid and must retain original bytes.
Parse the query successfully: exactly one nonempty decoded sig, no whitespace
in sig; reject bad escapes and decoded controls in any query component.
Preserve safe encoded path and the ENTIRE raw query byte-for-byte when sending,
including order, encoding case, duplicates of non-sig keys and legitimate
parameters. Do not normalize/reassemble it or strip/re-add sig.

No token Authorization header, Idempotency-Key, cookies, redirects, proxy,
ambient client/credential, default Slack route or Jira route. Use only the
explicit approved normal-TLS/direct caller client, narrowed to the exact origin.
Constructor/configure/read/preview/queue never initiates native activity.
Native fixture represents protocol, never an actual Teams account/channel.
Adaptive Card 1.4 POST is the existing adapter's envelope and inert text/link.
Its 28*1024 serialized-byte cap is OUR adapter cap, not a universal Workflows
platform limit. Exact-cap accepted/one-byte-over no-POST checks use the unchanged
adapter, because canonical parser title limits preclude arbitrary large titles.

Native 202: accepted only. Unexpected 200, lost ACK, response-body timeout or 5xx
after possible POST: uncertain, receipt null. 401/403: failed/auth.
429: rate-limited/rate_limited with bounded Retry-After metadata only.
Redirect: blocked/scope, no second origin request. Other failures keep existing
conservative native semantics. Never store raw native bodies/messages or secret
query-component echoes, even a syntactically safe native error code.
