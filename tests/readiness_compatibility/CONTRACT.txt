CONDITIONAL-FIRST READINESS COMPATIBILITY
========================================
Independent test-author gate. Only this new package/runner/contract is authored.
It calls the public production evidence.PrepareReadiness against the owned real
S3 fixture, not an application mock or simulated AWS 403-success scenario.

Run from aspm:
  .\tests\readiness_compatibility\Test-ReadinessCompatibility.ps1 -RuntimeConfig '<private-storage-isolation-json>'
Private fields: endpoint,region,bucket,roles.{admin,core,ingestion}.{accessKey,secretKey}.
The runner alone reads them, restores process environment and redacts captured
output before persistence. Root Go dependencies are reused without any manifest
change. Missing configuration/capability/setup/cleanup fails, never skips.

Required sequence, for the selected object and supplied role identity:
  FIRST actual request: PutObject with If-None-Match:*.
  Successful PUT or native 412/PreconditionFailed: real GetObject confirmation
  must follow. A PUT 403 is a failure, never readiness success or read fallback.
  A successful PUT followed by GET 403 is also failure, never success.
  Existing readable sentinel bytes must survive unchanged.
No production HeadBucket/list operation or broad permission is required.

Observation boundary
--------------------
The pass-through tap preserves signed Host/path/body and real responses from
127.0.0.1:18335/aspm-isolation. It verifies the actual supplied signing identity,
conditional header, ordering, status and native error code. It does not fabricate
responses. Operator/admin only seeds, independently verifies and deletes exact
owned object keys. Every target has a random per-case suffix within raw/team-a/
or normalized/team-a/. Role controls use separate owned keys, not the selected
PrepareReadiness probe, and do not pollute that request-order trace.
Actual ingestion controls verify raw GET success/PUT 403 and normalized PUT
success/GET 403. No policies, other prefixes, buckets or native main roles change.

Compatibility rationale / limits
--------------------------------
AWS documents that an absent-key GET can return 403 to callers without
s3:ListBucket. This local store instead returned 404 for these permitted raw
reads. The regression therefore checks the real conditional-first sequence,
not a fabricated AWS response, added ListBucket permission or a live AWS claim.
Native permission/readability and sentinel controls are distinct from the
ordering defect. Full AWS account behavior, deployment readiness and native
service/Kubernetes changes are not certified here.
Existing readiness_bootstrap and all frozen roots/oracles remain untouched.
